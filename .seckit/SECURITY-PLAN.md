#### AUTH-C2 · Hash passwords with Argon2id (or bcrypt/scrypt as fallback)

**Standards:** ASVS 4.0.3: V2.4.1 · OWASP Top 10 (2021): A02 · CWE: CWE-916, CWE-759 · NIST: SP 800-63B 5.1.1.2

### Controls

#### UPLOAD-C1 · Validate type by file content against an allow-list

**Severity:** critical · **Level:** 1 · **Mitigates:** UPLOAD-T1 · **Platforms:** backend

**Standards:** ASVS 4.0.3: V12.2.1 · OWASP Top 10 (2021): A04 · CWE: CWE-434

Check the magic bytes / parse the file against an allow-list of expected types.
Never trust the file extension or the client-supplied Content-Type alone.
For images, re-encode them (which also strips metadata and polyglot payloads).

**Implement with `@seckit/node`:** detectFileType() and assertFileType()

**Verify**

- _test_ — A PHP/HTML file renamed to .jpg is rejected.
- _automated_ — none yet; verify manually

#### UPLOAD-C2 · Generate server-side file names; never use the client file name in paths

**Severity:** high · **Level:** 1 · **Mitigates:** UPLOAD-T2 · **Platforms:** backend

**Standards:** ASVS 4.0.3: V12.3.1 · OWASP Top 10 (2021): A01 · CWE: CWE-22

Store files under a random identifier (e.g. UUIDv4). Keep the original name only as
metadata, sanitized before display.

**Implement with `@seckit/node`:** safeStorageName()

**Verify**

- _semgrep_ — No path.join / open() using the uploaded file's original name.
- _automated_ — `seckit audit` checks this (`seckit.upload-c2.client-filename-in-path`, `seckit.upload-c2.python-client-filename-in-path`, `seckit.upload-c2.spring-client-filename-in-path`)

#### UPLOAD-C4 · Store uploads outside the web root with no execute permission

**Severity:** high · **Level:** 1 · **Mitigates:** UPLOAD-T1 · **Platforms:** backend

**Standards:** ASVS 4.0.3: V12.4.1 · OWASP Top 10 (2021): A05 · CWE: CWE-434, CWE-552

Use object storage (S3, GCS, ...) with private buckets and short-lived signed URLs, or a
directory outside the web root that the web server never executes.

**Verify**

- _manual_ — Upload location is not reachable as a static path and buckets are private.
- _automated_ — none yet; verify manually

#### UPLOAD-C5 · Serve user files safely (separate origin, attachment, nosniff)

**Severity:** high · **Level:** 1 · **Mitigates:** UPLOAD-T4 · **Platforms:** backend, web

**Standards:** ASVS 4.0.3: V12.5.2 · OWASP Top 10 (2021): A03 · CWE: CWE-79

Serve uploads from a separate (sandbox) domain, with `Content-Disposition: attachment`
for non-image types, an explicit safe `Content-Type`, `X-Content-Type-Options: nosniff`
and a restrictive CSP. Do not serve user-uploaded SVG or HTML inline from the app origin.

**Verify**

- _test_ — Download responses include nosniff and attachment headers.
- _automated_ — none yet; verify manually

#### UPLOAD-C3 · Enforce size limits and guard against decompression bombs

**Severity:** medium · **Level:** 1 · **Mitigates:** UPLOAD-T3 · **Platforms:** backend

**Standards:** ASVS 4.0.3: V12.1.1, V12.1.2 · OWASP Top 10 (2021): A04 · CWE: CWE-400, CWE-409

Enforce a maximum request/file size at the proxy and the application. For archives and
images, cap decompressed size, file count and pixel dimensions before processing.

**Verify**

- _config_ — Body-size limit is configured on the upload route.
- _test_ — An upload above the limit returns 413.
- _automated_ — `seckit audit` checks this (`seckit.upload-c3.multer-without-limits`)

#### UPLOAD-C6 · Scan uploaded files for malware

**Severity:** medium · **Level:** 2 · **Mitigates:** UPLOAD-T5 · **Platforms:** backend

**Standards:** ASVS 4.0.3: V12.4.2 · CWE: CWE-434

Scan files (e.g. ClamAV or a cloud scanning service) before making them available to
other users; quarantine until the scan passes.

**Verify**

- _manual_ — The upload pipeline has a scan step before files are published.
- _automated_ — none yet; verify manually

## Payments

### Threats

| ID | Threat | STRIDE | CWE |

| PAY-T3 | Price or amount tampering by the client | T | CWE-602, CWE-472 |
| PAY-T4 | Double fulfilment from retries, replays or race conditions | TR | CWE-362 |
| PAY-T6 | Card testing (carding) through the checkout | SD | CWE-799 |
| PAY-T8 | Card data leaked through logs, analytics or databases | I | CWE-532 |

### Controls

#### PAY-C3 · Verify webhook signatures and process each event once

**Severity:** critical · **Level:** 1 · **Mitigates:** PAY-T2, PAY-T4 · **Platforms:** backend

**Standards:** OWASP API Top 10 (2023): API10 · OWASP Top 10 (2021): A08 · CWE: CWE-345, CWE-347

Verify the signature with the provider's SDK against the **raw** request body and the
webhook secret, reject old timestamps, store processed event IDs to ignore duplicates,
and when in doubt fetch the object from the provider's API instead of trusting the payload.

**Implement with `@seckit/node`:** verifyWebhookSignature() (Stripe-compatible t=,v1= scheme) — or your provider SDK

**Verify**

- _test_ — A webhook with an invalid signature returns 400 and changes nothing.
- _automated_ — none yet; verify manually

#### PAY-C4 · Compute amounts on the server and verify them before fulfilment

**Severity:** critical · **Level:** 1 · **Mitigates:** PAY-T3 · **Platforms:** backend

**Standards:** OWASP Top 10 (2021): A04 · CWE: CWE-602, CWE-472

Clients send only item IDs and quantities. The server computes the price from its own
catalog (including discounts and tax), creates the payment, and before fulfilling checks
that the paid amount and currency match the order.

**Verify**

- _test_ — Changing the price in the checkout request does not change the charged amount.
- _automated_ — `seckit audit` checks this (`seckit.pay-c4.client-supplied-amount`, `seckit.pay-c4.python-client-supplied-amount`, `seckit.pay-c4.java-client-supplied-amount`)

#### PAY-C2 · Never log or store card data; keep only provider tokens and the last 4 digits

**Severity:** high · **Level:** 1 · **Mitigates:** PAY-T8 · **Platforms:** web, backend

**Standards:** PCI DSS 4.0: 3.3.1, 3.4.1 · ASVS 4.0.3: V7.1.1 · OWASP Top 10 (2021): A09 · CWE: CWE-532

Store provider customer/payment-method IDs and display data only (brand, last 4, expiry month/year).

**Verify**

- _manual_ — Logs and analytics events from a test checkout contain no card data.
- _automated_ — none yet; verify manually

#### PAY-C5 · Idempotent payment and fulfilment operations

**Severity:** high · **Level:** 1 · **Mitigates:** PAY-T4 · **Platforms:** backend

**Standards:** OWASP Top 10 (2021): A04 · CWE: CWE-362

Use idempotency keys when creating charges, and make fulfilment atomic (transaction or
unique constraint on the payment ID) so retries and concurrent webhooks cannot fulfil twice.

**Verify**

- _test_ — Delivering the same payment-succeeded event twice concurrently fulfils once.
- _automated_ — none yet; verify manually

#### PAY-C7 · Throttle and screen payment attempts against card testing

**Severity:** medium · **Level:** 1 · **Mitigates:** PAY-T6 · **Platforms:** backend

**Standards:** OWASP API Top 10 (2023): API6 · OWASP Top 10 (2021): A04 · CWE: CWE-799

Rate-limit payment attempts per account, IP and card fingerprint, enable the provider's
fraud screening, and add CAPTCHA or require login after repeated declines.

**Verify**

- _test_ — Repeated declined attempts trigger throttling.
- _automated_ — none yet; verify manually
